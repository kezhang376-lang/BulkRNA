# Bulk RNA-seq 代码审查与分阶段重构方案

审查日期：2026-10-27。范围：完整静态阅读 step1_shell.sh（99 行）和 step2_Rscript.R（728 行，末尾为空行）。未连接 Kubernetes，未运行分析，未修改原始脚本。本文是待确认的方案，不代表已验证真实数据或 Pod 环境。

## 1. 总体判断

现有 fastp → STAR → featureCounts → DESeq2 → GO GSEA 主线可以保留。但当前脚本混合了不同项目的路径、分组和个性化代码，尚不适合无人值守运行。优先解决样本身份、计数单位和比较结果溯源，再处理统计方案，最后增加调度和扩展分析。

严重程度：P0 = 可能静默改变样本身份或比较对象，正式运行前必须解决；P1 = 主要统计风险、阻断错误或结果失真；P2 = 可维护性、复现性和健壮性；P3 = 可选优化。类别与严重程度分别记录；程序能够运行不代表科学方法成立。下列“建议”尚未实施，涉及统计模型、过滤、阈值及样本处理的变更均需用户确认。

## 5. 建议的标准化结构与接口（仅设计）

保留根目录两个原始脚本，确认后再按字节复制到 legacy 并保存 SHA256。建议目录：

```text
BulkRNA/
  step1_shell.sh
  step2_Rscript.R
  legacy/                         # 原始快照，不在此重构
  config/
    run.yaml                      # context/namespace/pod/container/各自挂载路径/资源
    analysis.yaml                 # design、过滤、阈值、富集和作图选项
    references.yaml               # 物种、assembly、FASTA/GTF/index、注释版本
  metadata/
    samples.csv
    contrasts.csv
    genes.csv                     # 可选
    pathways.csv                  # 可选
  scripts/
    shell/                        # fastp、STAR、计数、QC、可选饱和度/片段统计
    R/                            # 验证、QC、DESeq2、GSEA、可选定制图
  workflow/                       # PowerShell preflight/upload/launch/status/fetch
  tests/fixtures/                 # 小型模拟 counts、乱序元数据、失败边界
  docs/
  logs/<run_id>/
  reports/<run_id>/
  manifests/<run_id>/             # 配置快照、版本、文件指纹、执行状态
  README.md
  AGENTS.md
  .gitignore
```

服务器逻辑布局建议为 <remote_project_root>/runs/<run_id>/{scripts,config,metadata,logs,status,qc,counts,analysis}，原始 FASTQ 在独立输入位置保留；BAM/clean FASTQ/临时文件放项目中明确规划的大文件目录。正式目录与保留策略确认后才创建。

两个 Pod 即使看到同名 /home/zhangke，也不能据此断定底层数据共享。先查挂载及读取权限，再在授权的项目测试目录做唯一标记的双向读写验证；若挂载路径不同但底层相同，用 shell_project_root/r_project_root 显式映射。若不共享，优先只传 counts、QC、metadata、配置等小型文件，比较大小和 SHA256 后衔接，避免搬运 BAM。

配置边界：

- run.yaml 只存运行定位和资源；不存认证内容，不读取或输出 kubeconfig 原文。
- samples.csv：sample_id,group,fastq_r1,fastq_r2，可选 batch,subject,lane；多 lane 用独立清单关联生物学样本，不能当生物学重复。
- contrasts.csv：contrast_id,factor,numerator,denominator；正 log2FC 表示 numerator 相对 denominator 上调。复杂交互对比需单独设计，不能强行套简单组对比。
- analysis.yaml：保留当前 ~group、FC=1.5、raw p=0.01 作为 legacy 记录；正式采用哪种过滤、FDR 和设计留待确认，不能把建议值直接当已批准默认。
- references.yaml：species、assembly、annotation_release、路径、校验信息、STAR index 元数据、OrgDb/keyType。
- Windows 路径只服务本地维护；Linux 路径只服务 Pod 执行。上传前验证配置，不能把任意 CSV 文本直接拼进 shell 命令。

主要模块验收契约：

| 模块 | 输入 | 必须验收的输出 |
|---|---|---|
| preflight | 配置、样本表、参考、环境 | 缺失项/权限/容量/版本/共享存储检查记录 |
| fastp | 明确配对 FASTQ | 每样本 clean pair、有效 JSON/HTML、前后 reads 统计 |
| STAR | clean pair、经确认 index | 非空且可读 BAM、Log.final.out、样本级计数和比对 QC |
| featureCounts | 明确顺序 BAM、GTF、计数策略 | 原始表、summary、唯一基因×唯一样本整数矩阵和分配率 |
| R QC/DE | counts、按 ID 对齐的 metadata、已确认设计 | QC、模型 RDS、完整基因表、对比结果、图及版本 |
| enrichment | 指定对比的完整排序结果、基因集 | 每对比结果/RDS、映射和排序诊断，空结果状态 |
| collect | run manifest、模块输出 | 小型结果、校验清单、日志、状态及可审查报告 |

长任务不能仅依赖一直打开的 kubectl exec 会话。先核实 Pod 内现有作业管理和持久卷条件，再设计后台 launcher，保存 PID/启动时间/退出码/日志及 running/succeeded/failed 状态；状态文件需原子更新。Pod 被重建后旧 PID 无效，不能仅凭 PID 判定仍在运行。按本项目边界不创建 Kubernetes Job/Pod，也不改资源配置。kubectl 超时或断线后先查远端状态，禁止直接重复启动。

## 6. 分阶段改造与验收

1. **确认审查与输入契约**：补齐样本、建库、参考、软件信息，决定统计方案。产物为经确认配置规格和样本表，不运行正式数据。
2. **原始快照和最小骨架**：配置解析、样本验证、日志和 run manifest；保持原脚本。用模拟 counts 测试乱序元数据自动对齐、缺失/重名拒绝、空对比拒绝；不要求先部署 Snakemake。
3. **Shell 最小重构**：按原顺序拆 fastp/STAR/count/QC，修复错误传播、命名、解析及重跑行为；小型 FASTQ 或已知 BAM 验证，比较计数单位和样本名。任何计数策略差异单独解释。
4. **R 基础重构**：先独立 QC、单次 DESeq2 拟合和多对比，再独立富集及定制图。程序性修复与统计变化分开记录；改变过滤、FDR、模型时保留 legacy 对照并报告差异来源，不能要求两种方法得到完全相同的 DEG。
5. **跨 Pod 小规模集成**：在用户指定 Pod、独立测试目录验证共享/传输、退出码、失联恢复、禁止重复启动、结果取回和校验。阶段运行前明确数据集和资源预算。
6. **正式验证和扩展**：小型真实数据验收后再跑正式项目；基础稳定后评估 Snakemake 的跨 Pod 执行方式及模块扩展。固定镜像/包版本与参考快照，最终报告保留所有科学参数和未解决限制。

自动修复仅限明确程序问题且有限次数；模型不满秩、样本错配、建库策略未知、统计方案争议、参考不匹配时停止并说明原因，不自动换阈值、删样本、降级方法或覆盖旧结果。

## 7. 需要用户提供的信息

第一批（决定模型与输入，可先提供，无需现在创建 Pod）：

1. 本次真实项目 ID、物种；是沿用脚本中的小鼠项目还是另一个项目。
2. 样本表：每个 sample_id、实验组、生物学重复、是否技术重复/多 lane、批次、配对个体及其他关键协变量；原 sample_list_RNAseq.csv 和 sample_group.csv 也可用于核对。
3. 比较列表：处理组/对照组、方向，以及是否有配对、时间序列或交互作用需求。
4. FASTQ 所在目录、准确文件名示例、PE/SE、读长、建库链特异性、poly(A)/rRNA depletion、是否 UMI。
5. FASTA、GTF、STAR index 的实际来源和版本；index 的生成记录（尤其 STAR 版本和注释）。
6. start_fastp.py 与实际 fastp config；如已有 counts，可提供表头和少量行用于接口检查。
7. 对科学方案的选择：保留何种低表达过滤；主判据是否采用 FDR；FDR/FC 阈值；GSEA 排序和基因集参数；指定基因图是否仅展示或另做正式检验。当前 p=0.01、FC=1.5 只是脚本现状。

执行前第二批：

8. 用户手动创建的 Shell Pod 与 R Pod 名称、namespace、必要时 container 和预期 context（只提供名称，不提供密钥/证书）。
9. 两个 Pod 的挂载路径、共享存储关系、可写项目目录、CPU/内存/磁盘限额及持久性。
10. 软件版本或允许之后进行只读版本检查；是否能使用已有后台运行工具、包依赖是否齐全。
11. 输入规模、现有结果的保留范围、run_id 规则、Windows 需要取回的文件及体积限制。
12. 可选 gene/pathway 清单、期望图形与报告；第一版需不需要除 GO GSEA 外的富集模块。
